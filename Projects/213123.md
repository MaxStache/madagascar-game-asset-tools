● Based on the resolver logic in FUN_00432f70, and backed by the fact that no 
  real script in your logs ever writes a bare scalar to a Pair-type field — I
  checked, and every use of [location] / [scale] either supplies a full Pair16: 
  (x, y) literal or copies from another sprite's whole Pair field; there isn't a
  single instance of field[0x0a] to <number> without a .sub[] anywhere in
  out.txt.

  Here's why, and what actually happens:

  The reference bitfield has a separate sub selector (bits 0-5) from member
  (bits 8-13). Looking at FUN_00432f70, the whole "step into the compound value
  and pick a component" branch is gated by:

  else if ((param_2 != 3) && ((uVar5 != 0 || ((*param_1 & 0x3f) != 0)))) {
      ... // only runs if sub != 0 (or scope != 0)

  If sub == 0 (i.e. you write field[0x0a] with no .sub[...]), that whole branch
  is skipped. The resolver never dereferences into the Pair sub-object at all —
  it just returns the raw member-array slot address for pixel extents as-is.

  Given how location/scale/pixel extents are actually laid out (an embedded
  compound value with its own tiny vtable, where sub=1 → x and sub=2 → y, both
  computed as offsets from that embedded object), the slot you'd get back with
  sub=0 is the compound object's own identity slot — not x, not y, not "both."
  The interpreter (FUN_0043fd20) then just blind-copies raw bytes from your 15
  operand into that address.

  So: SET VALUE self.field[0x0a] to 15 would set neither x nor y extent to 15.
  It would write 15 into whatever the compound value's own header slot is, which
  isn't a coordinate at all — most likely corrupting that field (and crashing
  or misbehaving the next time pixel extents is read), not doing anything
  useful.

  To actually do what you probably want:
  - Both x and y → SET VALUE self.[pixel extents] to Pair16: (15, 15)
  - Just x → SET VALUE self.field[0x0a].sub[0x01] to 15
  - Just y → SET VALUE self.field[0x0a].sub[0x02] to 15

  Caveat: this is a logical deduction from the decompiled resolver, not
  something I traced by actually executing it in a debugger — but it's
  consistent with every real script in your corpus carefully avoiding exactly
  this bare-scalar-on-a-Pair pattern.
